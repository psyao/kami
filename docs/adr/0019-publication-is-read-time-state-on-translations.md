# Publication is read-time state on Translations, with no working copy in the MVP

A Translation's `status` (ADR 0013) takes two values only, `draft` and `published`. A Translation is **visible** when `status = published` and `published_at <= now()`, evaluated at read time, so nothing visitors see waits on a Tick (ADR 0020). "Scheduled" is not stored: it is a published Translation whose `published_at` is still to come. Publishing without a date sets `published_at = now()`, and editors may backdate. Unpublishing sets `status = draft` and keeps `published_at`, so "published at least once" (ADR 0008) stays true and republishing keeps the original date. `published_at` is both the date shown to visitors and the moment the Translation goes live. The whole predicate lives in one internal class, `Psyao\Kami\Content\Internal\Visibility`, which the ADR 0012 scope, `isVisible()` and the next-change computation below all use.

There is no working copy in the MVP. Saving a Published or Scheduled Translation changes what visitors see, so it takes `kami.entries.{type}.publish`, not only `update` (ADR 0014). A User without `publish` edits Drafts only, and sees Published and Scheduled Translations read-only. Global Sets are always published, so editing them takes `publish` too, and their navigation item is hidden without it. `SaveEntry` enforces it whoever calls: it refuses `status` and `published_at` on a Global Set and publishes every save. In the admin, what a Permission keeps from a User holds on the server, not only in the form: `EntryResource::save()` leaves `published_at` and a locked Shared Field out without `publish`, and `parent` without `reorder`, whatever input sent them, since a site's `EntryForm` can lose a generated input's `disabled`. Left out rather than refused, as a disabled input is: every save sends the form's value back, so a refusal would have to compare it with the stored one across formats and time zones. This takes simplicity (principle 6) over stability (principle 5): a site's own input loses a typed value with no error, which keeping the component `field()` gives avoids. A Draft's date therefore comes from a holder of `publish` or from code, and publishing reuses it. `SaveEntry` writes no Shared value a save did not ask for: a Shared default applies only when the Entry is created, and stored values of a hidden Field are cleared only by a save that gives its target, which a User under the lock cannot. So a later declaration never lets a User without `publish` change a Published Translation, and needs no Permission in `SaveEntry` (ADR 0011). This takes security (principle 1) over simplicity (principle 6): a value left hidden by a later condition stays readable until the target is next saved, and existing Entries get a default only from code that saves it. The safety net before saving is the Preview: the admin serialises the unsaved form into an `EntrySnapshot`, keeps it in Laravel's cache under a random token for one hour, and renders it through `ContentType::render()` (ADR 0009) for that User only.

**Concurrent edits.** With no working copy, two editors saving the same Entry would overwrite each other in silence. `SaveEntry` takes an optional `updatedAt`, the Entry's `updated_at` as its caller loaded it, and refuses with a `ValidationException` on `updated_at`, naming the Last modifier and the time in the Site's time zone, when the Entry changed since. The Entry is compared, not the Translation, so a save in another Locale counts: Shared Fields are written from any of them. Every save therefore touches the Entry's `updated_at`, a save changing a Translation only too. Omitted, as by imports, seeders and the CLI, nothing is checked. The admin's edit page passes the date it loaded, keeps the one each of its saves writes, and shows the refusal on a notification, since no input holds that date. The name is the panel's for that User, which `KamiPlugin` hands the core as a callback (ADR 0011); a save from code, or by a User deleted since, names nobody. The check reads the column with no lock, to the second it holds, so two saves within the same second can both pass. This takes simplicity (principle 6) over stability (principle 5): closing that window takes a version column or a lock around the read, for two people clicking Save within one second.

## Considered options

- **A working copy over the published version** (Statamic, Craft, Kirby): a `kami_working_copies` table holding a serialised snapshot, and a "Publish changes" action. It is half of revisions, which are deferred to V1 (deferral triage), and none of the three reference sites has an editor without `publish`. Rejected for simplicity (principle 6); it returns in V1 as a pending revision written by the same `SaveEntry` from the same `EntrySnapshot`.
- **Saving a visible Translation with `update` alone.** Simpler, but it lets a User who cannot publish change public content, which breaks the separation of ADR 0014. Rejected for security (principle 1) over simplicity (principle 6).
- **A version column, or a lock around the concurrent-edit check.** Exact where `updated_at` stops at the second, but it adds a column every write increments, or a lock each engine takes differently, against a window of one second between two editors. Rejected for simplicity (principle 6) over stability (principle 5).
- **A third stored status for Scheduled, flipped by a task.** It would make visibility wait on the scheduler, which the brief forbids.
- **Ancestor visibility inside the scope**, through a recursive CTE on every query. It weighs on the 15-query budget on three engines. An invariant enforced at write time (a child publishable only under a visible parent) does not hold over time once parents are scheduled or unpublished later.

## Consequences

- **Ancestors.** The scope checks the Translation only. Visibility at a URL includes ancestors (ADR 0008), and `$entry->url()` returns `null` when an ancestor is not visible, so Kami's components, Menus, the sitemap and feeds leave such an Entry out. A site listing that builds its own links can still show a link that answers 404: a documented limit. The admin's "Unpublish" confirmation on a Parent lists the visible children that become unreachable.
- **Next visibility change.** The core actions recompute, after commit, the earliest future `published_at` of the Site's published, non-trashed Translations (one query on an index on `kami_translations(status, published_at)`), and write it to a file under `storage/` that can be read with no query. Every cached page is stale once that moment has passed. Invalidating the whole page cache is deliberate: `render()` may query anything (ADR 0009), and a scheduled post appears on the home page, Archives and feeds. The cache mechanism belongs to "Cache, invalidation and performance budget".
- **Side effects of a scheduled publication** (extension event, sitemap, later webhooks) run from a Scheduled task, `kami:announce-publications`, on the first Tick after the moment, over the window `(last run, now]`, for Translations saved while still Scheduled (`updated_at < published_at`). An immediate publication fires them in the action. The first run starts its window at `now()`.
- **Doors for V1.** Scheduled unpublication adds a nullable `unpublished_at` column and one condition in `Visibility`. Revisions store `EntrySnapshot`s in a `kami_revisions` table with bounded retention. A working copy is a pending revision. Autosave and responsive side-by-side preview build on the same Preview.
- **Shared hosting and server.** Nothing differs: visibility is a `WHERE` clause, the next-change file is a filesystem read, and only the delay-tolerant side effects wait for a Tick.
