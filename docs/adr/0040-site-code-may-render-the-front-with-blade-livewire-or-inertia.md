# Site code may render the front with Blade, Livewire or Inertia, on cached pages under the strict CSP

Kami's front is sessionless Blade: the page cache serves pages as static files before Laravel boots (ADR 0021), one strict, nonce-free CSP covers every front page (ADR 0018), and Forms post plain HTML with no session (ADR 0015). `render()` returns any response (ADR 0009), so a site could already return a Livewire page or an Inertia response, but nothing said whether it would survive the page cache, the CSP or a Form. aguet.dev dropped Velox's Livewire contact modal during M9 for that reason (#559, #560), and Steve asked for Blade, Livewire and Inertia to be first-class (#571). The brief keeps the public front "Blade only at first, without Livewire" while asking that the architecture not prevent adding Livewire later. This ADR opens that door for the site's code: what Kami ships stays Blade.

**Kami guarantees that a site's own Livewire components and Inertia pages work on Kami's pages, on both mounts, and tests it in CI.** The default mount (`Kami::routes()`, sessionless and page-cached) is the main target; the session mount (`Kami::routes(session: true)`, ADR 0038) is covered as well, for what needs the visitor's state. Kami itself ships no framework JS: the `x-kami::` components stay plain Blade, the starter kit loads neither Livewire, Inertia nor Alpine, and the `Video` facade stays Kami's only front script (ADR 0009). A starter kit per stack was weighed and left out: three public surfaces to keep stable for a choice each site makes once.

A throwaway prototype on Livewire 4.4.8 and Laravel 13.42 (#571) settled the facts the design rests on:

- **A cached Livewire snapshot works for the next visitor.** Its checksum is an HMAC with the application key, not with the session, and Laravel 13's `PreventRequestForgery` accepts a POST carrying `Sec-Fetch-Site: same-origin` without a token. A visitor with no cookie at all who clicks a component of a cached page gets a 200. A `cross-site` or `same-site` request gets a 419, and so does a browser that sends no Fetch Metadata header, since the cached page carries no valid token.
- **The page cache stored Livewire's page without its assets.** Livewire injects its script and style on `RequestHandled`, after `CachePages` had stored the response, so every visitor after the first got an inert component. The mechanism is the one behind #434. The page cache now stores the response as it is sent, from the middleware's `terminate()` (ADR 0021, amended).
- **Livewire's update route always runs the `web` group.** Livewire adds it to any update route, so the first click on a component starts a session.
- **The strict CSP holds for Livewire under four conditions** (ADR 0018, amended).
- **The page cache served cached HTML to Inertia's `X-Inertia` requests**, since it keys on the host and the URI only. Inertia's JSON gets a cached variant of its own (ADR 0021, amended).

The decisions:

- **Livewire on the default mount.** A component in a cached page works as is. The page itself sets no cookie and stays cached. The first click on a component reaches Livewire's update route, which sets `laravel_session` and `XSRF-TOKEN`. Kami accepts it: the cookie follows the visitor's own action on a component that needs it, so it is strictly necessary, not the non-essential cookie principle 2 forbids. ADR 0021's "an anonymous visitor gets no cookie" still holds for every page Kami renders. Later pages stay served from the cache, which ignores the cookie on sessionless routes. A Kami route that bypassed Livewire's `web` group, protected by ADR 0015's origin check instead, was rejected: Livewire forces the group back on, so the bypass would break with its minor releases, trading stability (principle 5) for a cookie the visitor triggers.
- **Sessions move to the `file` driver.** The starter kit set Laravel's default `database` driver, chosen by no ADR when only editors had sessions. A visitor session would write `ip_address` and `user_agent` into the `sessions` table, against principle 2 and against what Kami does elsewhere (no IP on Submissions, truncated IPs in the Audit log), and every request with a session would pay a round trip to the remote database, the reason the cache already uses `file` (ADR 0021). The `file` driver keeps the payload alone, on the local disk, pruned by the same lottery. The starter kit sets `SESSION_DRIVER=file`; existing sites change their `.env`, which signs every editor out once, as `UPGRADING.md` says. Privacy (principle 2) wins over stability (principle 5). Kami offers no list of active sessions, the one feature that would need `database`. Several web servers share `storage/`, as the page cache already requires.
- **Inertia on the default mount.** `Kami::routes(middleware: [...])` adds the site's `HandleInertiaRequests` (or any rendering middleware) to the Entry and Archive routes of either mount, never to the Tick, the Feeds, the Conversions or the Form route (ADR 0038, amended). Appending to the `kami` group in `bootstrap/app.php` was rejected: the group's order would become public API, the addition would reach Feeds and media, and `KamiServiceProvider` declares the group at boot, so an append can be lost silently. Simplicity (principle 6) wins over the Laravel-native idiom (principle 8). On the default mount, the site's shared props must not read the session, and Inertia's `errors` prop is empty. The page cache stores the JSON variant beside the HTML (ADR 0021, amended).
- **Inertia renders in the browser on shared hosting.** Inertia's server-side rendering needs a persistent Node process, which shared hosting forbids. Kami guarantees client-side rendering on both environments; on a server, SSR stays the site's to run and supervise, and the page cache stores its HTML like any other, untested by Kami. Without SSR an Inertia page shows nothing without JS, so a site choosing it gives up the brief's "no JS required to show the content" for those pages: the trade is the site's, and the guide names it and points content pages on shared hosting to Blade or Livewire. Kami's own budget is unchanged. `<x-kami::seo />` in the Blade root view renders the first load's meta tags.
- **Forms from a component or a page.** The route's visitor checks, the honeypot, the origin Entry, the per-IP throttle and validation, move into a public action, `Psyao\Kami\Forms\Actions\SubmitForm`, which the Form route calls (ADR 0015, amended). A Livewire action calls it and gets Laravel's `ValidationException`, which Livewire shows natively. An Inertia page posts to the Form route's JSON answers (#599) with `fetch`: Inertia's `useForm` expects an Inertia response, with a redirect and errors in the session. Security (principle 1) wins over simplicity (principle 6): one more public class, so that no site's Livewire form has to rewrite the throttle, since a bot can read a cached snapshot and post it with forged headers.
- **One strict CSP.** No per-response policy: Livewire fits ADR 0018's policy under its four conditions, so no concrete need opens the door that ADR left. Alpine on its own follows the same rule through its CSP build.

## Considered options

- **Compatibility through the session mount only** (ADR 0038 as it stands). Nearly true already, but each reference site would lose the page cache for one component: about 170 ms of server time instead of 30 ms or less on Infomaniak without OPcache (ADR 0021).
- **Kami ships Livewire or Inertia components, or a starter kit per stack.** A dependency more and three surfaces to keep stable (principles 5 and 6), for what a site's own code covers.
- **`spatie/laravel-responsecache`'s model** (v8), looked at again for this question: replacers that put fresh values into a cached page, and stale-while-revalidate. A replacer needs the framework booted on every hit, and its CSRF replacer a session; Kami's reader runs before boot. Laravel 13's origin check made the CSRF replacer unnecessary anyway. ADR 0021's rejection stands.
- **Bypassing the page cache for every `X-Inertia` request.** One line in the reader, but an Inertia site's navigation would pay the uncached budget on every click, and the cache would serve first visits only.
- **A `kami:doctor` warning for Inertia without SSR.** The doctor cannot see what `render()` returns without rendering pages, and it would police a legitimate choice.
- **Recipes only for Forms**: `validate()`, `StoreSubmission` and the site's own `RateLimiter` in a Livewire action. Each site would rewrite the throttle and the honeypot, or forget them.

## Consequences

- **The guide.** `docs/guide/front-stacks.md` holds the Livewire and Inertia recipes for both mounts, the four CSP conditions, the cookie a click sets and the 419 of browsers without Fetch Metadata, client-side rendering and SSR, and `SubmitForm` from a Livewire action.
- **`kami:doctor`** warns when Livewire is installed without `csp_safe`.
- **Tests.** The `Kami` suite checks the contract over HTTP on both mounts:
  - a cached Livewire page keeps its assets, a cookie-less same-origin update gets a 200, and a cross-site one a 419;
  - Inertia's JSON variant is stored apart, served only to its asset version, never for a partial reload, and an `X-Inertia` request never gets the HTML;
  - `SubmitForm` runs from a Livewire action.
  The `Browser` suite clicks a real Livewire component under the strict CSP, with no CSP violation in the console: Livewire's bundle changes with its minor releases, and only a browser proves the four conditions. `inertiajs/inertia-laravel` (MIT, maintained by the Laravel team, pure PHP) joins `require-dev`; no Inertia JS build, since Inertia's contract is an HTTP contract.
- **Shared hosting.** Livewire runs in the request, with no process: its update requests boot Laravel and stay within the uncached budget, and its sessions are files. Inertia renders in the browser only. The page cache serves the HTML and the JSON variant of cached pages before boot, OPcache off or not.
- **Server.** The same, with OPcache making boots cheaper. Inertia's SSR is possible as the site's own process. Several web servers share `storage/` for sessions as for the page cache.
- The work lands in M10 (#610 to #614), before Blocks, the `Video` facade and the Archives and Feeds in the page cache, which rest on the amended ADRs.
