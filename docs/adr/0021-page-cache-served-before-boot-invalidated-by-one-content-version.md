# The page cache is served before Laravel boots and invalidated by one content version

On Infomaniak shared hosting OPcache is off, so every PHP-served request recompiles Laravel and Filament, and the database is remote. Measured on aguet.dev (Velox, no page cache), a page takes about 170 ms of server time. The brief asks that a cached page avoid a full application boot. So Kami ships a full page cache in the MVP, although the comparatif lists it under V1, because the brief ranks above the comparatif. A file of the package, required by one line in `public/index.php` right after Laravel's maintenance check, serves cached pages with no autoload and no framework: it reads a manifest, compares the clock with its expiry, and sends the stored headers and body from `storage/framework/kami/pages/`. Kami's public middleware writes the cache, and serves from it too when a request reaches Laravel.

Invalidation needs no tags. One **content version** covers the whole installation, all Sites included, and every cached file is keyed by it. Any write through a core action makes a new version: Entries, Terms, Media metadata, Menu items, Redirects and Global Sets. So does every `kami:install`, because views may have changed, and so do `Kami::flushCache()`, `kami:cache:clear` and `optimize:clear`. The manifest also holds the next visibility change (ADR 0019), so ADR 0019's file and the manifest are the same file. The first request after that moment goes through Laravel. It recomputes the next change in one indexed query and writes a new version. A stale page is therefore never served, and scheduled publishing still waits on no Tick (ADR 0020).

The decision trades simplicity (principle 6) for performance (principle 7). Kami owns a small cache reader outside the framework, plus a line that the starter kit puts in `public/index.php` and that a host application adds by hand. In return a cached page skips the boot. Invalidation stays coarse: any write empties everything. That is deliberate, because `render()` may query anything (ADR 0009), and a write on a small site is rare next to its reads.

## Considered options

- **Static HTML under `public/`, served by Apache with no PHP.** This is the fastest option, but Apache cannot know that a scheduled publication's moment has passed, and a hit runs no PHP, so it fires no visit Tick (ADR 0020). On a site with no cron and no task planner, a page would stay stale with nothing left to refresh it. Rejected because visible behaviour would wait on the scheduler.
- **`spatie/laravel-responsecache`** (MIT, maintained, Laravel 13). It is a middleware, so every hit still pays the full boot. It stores serialised `Response` objects that a reader running before boot cannot read. Without tags, its `clear()` flushes the whole configured store (research `candidate-dependencies`, note 4), which would also drop the Tick and Conversion locks. It has no notion of an expiry moment. Rejected under principle 8: the central need is not covered. Host applications stay free to use it on their own routes.
- **A Kami middleware only.** It saves rendering and queries but not the boot. It remains the fallback when a host application leaves the `index.php` line out.
- **One version per Site, or invalidation by dependency.** The reader cannot map a host to a Site without booting, and multi-site installations are rare. Dependency tracking is the comparatif's V1 "smart invalidation".

## Consequences

- **Kami's public routes run without a session.** `Kami::routes()` registers them outside the `web` middleware group, in a `kami` group with `ResolveLocale` and without `StartSession`, CSRF or cookie encryption. An anonymous visitor gets no cookie (principle 2), and a response that sets a cookie is never cached. A front form needs no session either. With no session there is no ambient credential for a forged request to abuse, so a session CSRF token protects nothing there. Kami's form route checks `Sec-Fetch-Site: same-origin`, falling back to the `Origin` header, which is the same check as Laravel 13's `PreventRequestForgery`, applied to that route only. A page with a form therefore stays cacheable. The admin keeps the `web` group, its session and its CSRF tokens.
- **What is cached.** Only `GET` and `HEAD` requests with no query string and no `Authorization` header. Only 200 responses of Kami's public routes: Entries, the first page of Archives, and Feeds. Only when the request host is the resolved Site's host, so forged `Host` headers cannot fill the disk. A response is skipped when it calls `Kami::withoutPageCache()`. Redirects, 4xx pages, Preview, the Tick route and Conversions (already static, ADR 0017) are never cached. Stored headers (CSP, security headers, `Content-Type`) are replayed, except `Set-Cookie` and `Date`. The reader sends an `ETag` made of the version and a hash, answers 304 to `If-None-Match`, and sends `Cache-Control: no-cache`, so browsers revalidate and never show a stale page. Each cached page also expires after one hour at most, as a net for what Kami cannot see (host data, time-dependent content).
- **On by default.** `kami.page_cache.enabled` is `true` unless `APP_DEBUG` is on.
- **Ticks.** The reader checks the `tick-*` files with `filemtime()`. When the last Tick is older than five minutes, it lets the request reach Laravel, which serves the cached body and runs the visit Tick through `defer()`. That costs at most one full boot every five minutes.
- **Disk.** Files of old versions are deleted through `defer()` after a new version is written, and a Scheduled task prunes them as a backstop. Files are written atomically (temporary file, then rename). There is no lock against a stampede when a page expires. The number of cached files is bounded by the number of Paths.
- **Fragments.** Kami caches nothing of its own on the front: the 15-query budget holds cold. Site code gets `Kami::remember($key, $ttl, $callback)`, which prefixes the key with the content version, so fragments go stale with pages and need no tags. Orphaned keys expire by their TTL. The starter kit sets `CACHE_STORE=file`, because the `database` store pays a round trip to the remote database on every read.
- **Shared hosting and server.** The mechanism is the same on both. With OPcache on a server, the reader costs almost nothing. Cache files live on the local disk, so an installation behind several web servers either turns the page cache off or shares `storage/`.
