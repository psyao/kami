# Robots and sitemap are static files Kami writes, behind one indexable switch

On Infomaniak shared hosting, a missing `public/robots.txt` is answered by the host itself, before the request reaches Laravel (retrospective §2.8, Velox A22). So Kami's `/robots.txt` is a static file and has no route. `kami:install` writes it on every deploy when it is missing or when its first line is the marker `# Managed by Kami (kami:install). Delete this line to own this file.` Without the marker the file belongs to the site, and Kami never touches it again (Velox A7). The sitemap is static too. `public/sitemap.xml` is always a sitemap index over `public/sitemaps/{locale}-{n}.xml`, with at most 10,000 URLs per file. The files are streamed with `XMLWriter` in keyset order on the Entry's ULID, and Apache serves them without PHP. One switch, `config('kami.indexable')`, set by `KAMI_INDEXABLE` and defaulting to `app()->isProduction()`, decides whether search engines are welcome. It drives `robots.txt`, a site-wide `X-Robots-Tag` header and the robots meta tag.

The decision trades simplicity (principle 6) for stability (principle 5). Kami writes files into `public/` and keeps their freshness itself, where a route would be simpler. In return, the robots rules hold on the host the reference sites run on, and a crawler reading a 30,000-Entry sitemap costs no PHP and no query.

## Considered options

- **A dynamic `/robots.txt` route, with a documented "ship a static file on Infomaniak" step** (Velox). This is exactly what broke aguet: once the file was deleted, the host's answer replaced Kami's, without `Disallow: /admin` and without the sitemap.
- **A sitemap built on each request** (Velox). That means 30,000 rows per crawler visit on a host with no OPcache, and more at the 1 M design target.
- **One `urlset` below 50,000 URLs and an index above.** Two shapes to keep, and `/sitemap.xml` changes kind the day a site grows.
- **Rebuilding the sitemap on save**, in the request or through `defer()`. Saves would wait or burn the shared-hosting time budget after the response, since the timer keeps running after `fastcgi_finish_request()`. Bursts of saves would rebuild again and again. Scheduled publications need the Tick anyway. No search engine reads a sitemap often enough for seconds of freshness to matter.
- **Noindex outside production only, with no switch.** That gives no way to check the real output on staging (Lighthouse, Open Graph validators), and no way to keep a production site out of search engines before launch.

## Consequences

- **Robots content.** When indexable, `robots.txt` holds `User-agent: *`, `Disallow: /{panel path}` (left out when the panel sits at the root or on its own domain), and `Sitemap: {Site URL}/sitemap.xml` as an absolute URL. When not indexable, it holds `User-agent: *` and `Disallow: /`. `Disallow: /` hides the `noindex` header from crawlers, so a copy that is already indexed would stay indexed. Staging copies and unlaunched sites, which were never indexed, are better served by not being crawled at all. The starter kit ships the managed file in place of Laravel's default.
- **Not indexable** also adds `X-Robots-Tag: noindex, nofollow` to every response of Kami's public middleware group (feeds and the sitemap included) and the robots meta tag to every page. Preview, Preview links and the admin panel always send `noindex, nofollow`, whatever the switch. Tests set `config(['kami.indexable' => true])` instead of faking the environment.
- **Sitemap freshness.** After commit, the core actions that change what the sitemap lists (publishing, unpublishing, Paths, hiding from search engines, Trash, deletion) touch a stale marker under `storage/`, and so does `kami:announce-publications` (ADR 0019). The Scheduled task `kami:sitemap` runs `hourly()` and does nothing unless the marker is newer than the last build. It builds into a temporary directory and swaps it in by rename, so a crawler never reads a half-written sitemap. When `public/sitemap.xml` is missing (a fresh install, before any Tick), the stock `!-f` rewrite hands the request to a Kami route that builds the files in the request, writes them and serves the index, as Conversions do (ADR 0017).
- **Volume ceiling.** The build is a full rebuild in one task run, which fits the 30,000 Entries guaranteed on shared hosting. At the 1 M design target, the build resumes across Ticks from the last file written, because Kami never relies on `set_time_limit()` (ADR 0020). This is an internal change.
- **Multi-site door.** One `public/` directory holds one `robots.txt` and one `sitemap.xml`. Several Sites on one installation (V1) need a per-host answer: the sitemap index moves behind the route, and `robots.txt` needs a host probe on Infomaniak first. Neither change touches the public API.
- **`kami:doctor`** reports a production install that is not indexable, a non-production install that is, a managed `robots.txt` that differs from what `kami:install` would write, a site-owned one without a `Sitemap:` line, and a sitemap stale for more than two hours.
- **Shared hosting and server** behave the same: Apache or nginx serve the files, and the rebuild runs in whichever Tick comes first. On nginx, the `!-f` fallback must be reproduced, as for `/media`.
- **Host applications.** When a host route already answers `/sitemap.xml` or `/robots.txt`, Kami does not write that file, and it exposes its per-Locale sitemaps through `Kami::sitemapUrls()` (ADR 0038).
