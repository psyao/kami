# Field values live in a table per Content Type, one row per scope

Each Content Type that declares at least one stored Field gets its own table, `kami_type_<handle>`, joined to the `kami_entries` envelope (ADR 0002) by `entry_id`. Each declared Field is a typed column, so the database knows its type, can index it, and sorts and filters it without JSON functions. A table holds one row per scope, keyed uniquely by `(entry_id, locale)`. The row with `locale = '*'` carries the Shared fields. One row per Locale (`'fr'`, `'en'`) carries the Translatable fields. In each row, the columns outside its scope stay null.

The schema follows the code through ordinary Laravel migrations. Losing a value then always takes a migration someone wrote and reviewed (psyao/velox#283, #284). Content model drift is checked by comparing the declarations against the schema, at a constant cost whatever the volume; the one scan is `kami:make:migration`'s, below.

This departs from Velox ADR 0002 (Field values in a JSON `data` column). The brief requires filtering and sorting at 1,000,000 Entries on three engines. With JSON, that needs a second, synchronised index, and every migration or drift check scans every row.

## Considered options

- **A JSON `data` column on the envelope** (Velox ADR 0002, Statamic, Craft 5). Adding a Field needs no migration. Filterable Fields would need an EAV index table kept in sync on save. Renames and removals would be PHP batch rewrites, and the drift check would have to scan rows. Velox also hit MySQL key reordering (A15, D8), and its `JSON_SET` migrations excluded PostgreSQL (§2.9). Rejected for stability (principle 5).
- **JSON plus generated columns.** `virtualAs()`/`storedAs()` take an engine-specific expression, and PostgreSQL before 18 has no virtual columns. This breaks the portability requirement.
- **Full EAV.** About 15 million rows at the design target, reads that must pivot rows into fields, and no typing.
- **Two tables per type, one for Shared fields and one for Translatable fields.** Switching a Field between the two would move a column between tables. Rejected for simplicity (principle 6): with one table, the switch is a data operation and needs no schema change.
- **Shared fields stored on the default Locale's row.** Changing a Site's default Locale would silently orphan them. `'*'` is a sentinel rather than `NULL` because a unique index lets several `NULL`s through on all three engines.

## Consequences

- **Table names.** A type handle is snake_case, 40 characters at most, checked at boot, so `kami_type_<handle>` stays within the identifier limits of PostgreSQL (63) and MySQL (64). Laravel's index and foreign key names append to the table name and exceed those limits, so `kami:make:migration` writes hashed ones (`kami_idx_<hash>`, `kami_fk_<hash>`). A table generated before keeps its names. A type with no stored Field has no table.
- **Columns.**
  - Each Field type class declares its Laravel column type (`string`, `text`, `integer`, `decimal`, `boolean`, `date`, `dateTime`, `json`).
  - Relation and Media Fields have no column: they live in `kami_references` (ADR 0005).
  - Every Field column is nullable and has no database default. A draft may be incomplete, so "required" is validated in PHP at publication; a save also may not blank a required Shared Field holding a value while another Translation is Published, as that Translation reads it. The default comes from the declaration, so changing it needs no migration.
  - A column is indexed only when its Field is declared filterable or sortable.
- **Structured values** (repeaters, rich text, blocks, option lists) are opaque `json` documents. SQL never queries them by JSON path, and PHP always compares them decoded, never as strings (Velox A15, D8). A value that must be filtered becomes a top-level scalar Field.
- **Universal values.** Values that every type has, and that cross-type subsystems read (title, slug, status, `published_at`, SEO meta), are core columns, never Fields in `kami_type_*`. Their per-Locale table is decided in "Multilingual content and fallback", SEO meta in "SEO".
- **Scope rule.** The write layer in PHP enforces that a Shared field stays null in Locale rows, and the reverse. The database does not enforce it.
- **Locale rows.** Adding a Locale to a Site creates no rows: a missing Locale row reads as an empty Translation, and its fallback is decided in "Multilingual content and fallback". A row whose Locale is no longer declared is kept. `kami:doctor` reports it without failing the deploy.
- **Loading.** Field values always load with the Entry, never lazily: strict lazy loading from day one (Velox I-286). A collection of one type costs one extra query. A collection of mixed types costs one query per type present.
- **`kami:make:migration {type?}`** diffs the declarations against the schema and writes an ordinary migration into the site's `database/migrations`. When a type loses one Field and gains another, it asks in a terminal whether this is a rename. Without a terminal, it refuses rather than guess. It changes a column's type only between `string` and `text`, which need no conversion: a value too long for a `string` stops the migration, stays whole on SQLite, and is truncated only on MySQL or MariaDB with `strict` mode turned off, a loss accepted against refusing the commonest retype (stability, principle 5, against simplicity, principle 6). Any other change it refuses, printing a migration to finish by hand: a value that does not convert has no portable answer, PostgreSQL refuses most of these casts outright, and MySQL and MariaDB accept them whenever the rows happen to convert. This trades simplicity (principle 6) for stability (principle 5). That migration runs from the CLI on shared hosting as on a server, updating row by row. SQLite reports a `json` column as `text` and MariaDB as `longtext`, so a column they report so and a Field declares `json` passes only while every value decodes to an array, which this command scans, and only it: telling a `Textarea` turned `Repeater` from a table already right trades simplicity (principle 6, a scan on a dev command) for stability (principle 5, no prose read as `null` then overwritten). A `json` column turned `text` stays unseen on SQLite, its values reading as text all the same. Types the package declares, such as the Site settings Global Set, ship their migrations in the package.
- **`Psyao\Kami\Schema\ContentMigrator`** provides the data operations a schema change cannot express:
  - `renameType($from, $to)`, which moves `kami_entries.type` and the table, with the index and foreign key names that follow the old handle, hashed or starting with its table's name as Laravel's do, so a new type can take that handle; any other name stays;
  - `renameField($type, $from, $to)`, which renames the column and the index hashed from its name for a stored Field, and rewrites `kami_references.field` for a relation Field. It tells them apart by the column alone, as the declaration has already changed: a mistyped relation handle changes nothing, and `kami:doctor` reports what is left;
  - `makeTranslatable($type, $field)`, which moves the `'*'` value to the declared Locales where the Entry has a Translation (creating missing rows), or to the default Locale when it has none, and then clears it. A row for each declared Locale would hold a frozen copy where Fallback should answer, once a Translation arrives there. A relation Field's shared rows move the same way, in pick order;
  - `makeShared($type, $field, keep: <locale>)`, which throws when another Locale holds a different non-null value, or a relation Field a different list of targets in pick order, unless `discardOthers: true` is passed. It checks every Entry before writing, an existing `'*'` value included, and refuses to keep `'*'` or a Locale nothing holds, discarding or not. `makeTranslatable` refuses to overwrite a different Locale value the same way;
  - `makeTypeTranslatable($type, locale: <locale>)`, which moves each `'*'` Translation to that declared Locale, and `makeTypeShared($type, keep: <locale>)`, which keeps that Locale's Translation as `'*'` and throws while another Locale's would be lost, unless `discardOthers: true` is passed. They serve a flipped `$translatable`. Field rows are left to the per-Field operations;
  - `dropType($type)` and `dropLocale($locale)`, refused while the type or Locale is declared, and for `'*'`. `dropType` removes the table, the Entries and what hangs off them, other types' links to them included. `dropLocale` removes the Locale's Translations, type rows, References and Paths.

  An Entry left without a Translation by `dropLocale` or `discardOthers` stays, answering nowhere, until one is written. Paths are derived, so these operations leave the rest to `SyncPaths` at the next `kami:install`.

  The operations run in batches through the portable query builder, with no JSON functions, no model events and no `updated_at` change; a batch that moves values is one transaction, so a conversion that stops can run again. `renameType` is the exception: it moves the Entries in one update, between moving the table and renaming its constraints, and a table still holding the old names is what tells a second run from two unrelated types. A longer lock on `kami_entries`, from the CLI, trades performance (principle 7) for stability (principle 5): batches would leave two types' Entries, which nothing tells apart for a type with no table. A foreign key is written again before its old one goes, so a stop loses none. A hand-written table with no name following the old one stays refused. They have no `down()`: going back means a new migration with the inverse operation. `makeShared` undoes `makeTranslatable` without loss as long as the Locales still agree, and the rename operations undo themselves with the arguments swapped. The drop operations destroy, by design.
- **Content model drift.** `kami:install` fails the deploy in any of these cases:
  - a declared Field has no column;
  - a column belongs to no declared Field;
  - a column has the wrong type;
  - a `kami_type_*` table belongs to an undeclared type;
  - a type's Translations do not match its `$translatable`: a Locale Translation on an untranslatable type or a `'*'` Translation on a translatable one, which would otherwise cost the type every 200 row at `SyncPaths`;
  - a Singleton or Global Set has several Entries in a Site, whose one address and page can answer for only one.

  It runs after `migrate`, before seeds and `SyncPaths`, and each failure names the type, the Field and the migration or `ContentMigrator` call to write. Its number of queries follows the declarations, not the Entries, and it reads no row into PHP. On a healthy site the `$translatable` check still probes each Entry of a type through an index, a duration that grows with them, far below `SyncPaths`, which reads them all; only a sample would be constant, and it would miss a conversion that stopped partway (stability, principle 5, over performance, principle 7). A declared index that is absent is not drift, and neither is a column declared `json` that SQLite reports as `text` or MariaDB as `longtext`, which only `kami:make:migration` scans. `kami:doctor` reports the same errors.

  Removing a Field from code therefore destroys nothing: the deploy blocks until a migration drops the column or the Field comes back. `kami:doctor` also reports Entries whose `type` is not declared.

  Values and links no read finds warn in `kami:doctor` without failing a deploy, as rows of an undeclared Locale do: a Field's value on the row its scope no longer reads, and relation rows under an undeclared handle or in the wrong scope. Finding them scans, so a deploy does not ask. A removed relation Field leaves rows no `ContentMigrator` call deletes, so failing on them would block a deploy with no remedy, and reading them at each deploy would break the constant cost above; the rows are kept, and the warning names them.
- **Shared hosting and server.** Migrations run from the CLI (`kami:install` in the deploy), never from a web request, so web time limits do not apply. MariaDB adds columns instantly. SQLite rebuilds the table for column changes, which Laravel 11+ handles natively. Nothing differs between shared hosting and a server.
- **Cost.** Every change to a Field takes a migration, and each Content Type adds one table. That is the price of typed, indexable columns and loss that is always explicit. It trades simplicity (principle 6) for stability (principle 5).
