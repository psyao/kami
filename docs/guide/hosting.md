# Hosting

Kami runs on shared hosting with nothing more than PHP, a database and SSH. One code path serves shared hosting and a server: a server only adds speed.

## What the host needs

- PHP 8.5 or later, on the command line and on the web, with the extensions [Installation](installation.md#requirements) lists. The two often run different PHP builds: check both.
- One of the [supported databases](installation.md#database).
- SSH access with Composer, to run `composer install` and `php artisan kami:install` on each deploy.
- A document root on the site's `public/` directory, and HTTPS.
- Write access to `storage/` and `bootstrap/cache/` for the user PHP runs as.

## What Kami does not need

- **No cron.** Kami's Scheduled tasks run from a Tick: `php artisan kami:tick` from a server's cron, a secret URL the host's planner calls, or visits; nothing visible waits for it ([Scheduler](scheduler.md)).
- **No queue worker.** Kami dispatches no job, and sends the password reset email itself rather than queue it ([Security](security.md#password-reset)). Your application's jobs on the `database` queue run from each Tick ([Scheduler](scheduler.md#the-queue)).
- **No Redis, Memcached or other daemon.** The starter kit uses the `file` cache store and the `database` session driver.
- **No Node on the server.** Kami's admin assets ship precompiled and `kami:install` copies them to `public/`. The site's own front assets are built before the deploy: see [Deployment](deployment.md#front-assets).
- **No `mail()` or `sendmail`.** Kami sends mail through Laravel's mailer, over SMTP ([below](#mail)).
- **No `exec` or `proc_open` on the web.** Shared hosts often disable them; Kami never calls them.

## Shared hosting and a server

| Subject | Shared hosting (Infomaniak Web Hosting) | Server (Cloud Server or VPS) |
| --- | --- | --- |
| **Install and deploy** | `kami:install` over SSH, under the command line's limits (no time limit on Infomaniak) | The same |
| **Admin assets** | Precompiled in the package, copied to `public/` by `kami:install` | The same |
| **Front assets** | Built by the site in CI or on the developer's machine, then copied with the code | The same |
| **Cache and sessions** | `file` cache, `database` sessions, as the starter kit sets them | The same; Redis or Memcached possible, never required |
| **Page cache** | Served by the line in `public/index.php` before Laravel boots: the manifest and one file read, about a hundred lines compiled with OPcache off ([Page cache](page-cache.md#serving-before-laravel-boots)) | The same; behind several web servers, share `storage/` or turn the page cache off |
| **`robots.txt`** | A static file `kami:install` writes over SSH, so Infomaniak never answers its own, which disallows nothing ([SEO](seo.md#robotstxt)) | The same; Apache or nginx serve it |
| **Sitemap** | Static files Apache serves, rebuilt hourly by a Tick when stale; built through the `!-f` rewrite when missing ([SEO](seo.md#sitemap)) | `kami:sitemap` hourly from `kami:tick` in cron; nginx needs the fallback below |
| **Conversions** | Generated by PHP on their first request, then served by Apache from `public/media` with the headers of its `.htaccess`; `kami:media:warm` over SSH, `kami:media:prune` weekly from a Tick | nginx serves them once given the rewrite and headers below; the same commands |
| **Image formats** | AVIF and WebP where GD or Imagick passes Kami's encode test, else JPEG or PNG alone | The same |
| **Dates** | Kami sets the application's time zone to UTC, whatever the host's default (`Europe/Zurich` on Infomaniak) | The same |
| **MFA** | Pure-PHP codes and an SVG QR code, no extension beyond Laravel's; the last code accepted and a lock per User kept in the `file` or `database` cache | The same, or Redis |
| **Sign-in throttling** | Attempts per IP address and per email counted in the `file` or `database` cache, with no daemon | The same, or Redis |
| **Audit log** | One insert inside each action's transaction; `kami:audit:prune` daily from a Tick, to apply the [retention](audit-log.md#retention) | The same |
| **Scheduled tasks** | Run in-process from a Tick, with no child process: the planner calls `/kami/tick/{token}` every 15 minutes at best, and visits start one after five minutes without ([Scheduler](scheduler.md)) | `kami:tick` from cron every minute |
| **Reset email** | Sent after the response through `defer()`, as PHP-FPM finishes the request first; under `mod_php`, before it | The same under PHP-FPM |
| **Submission mail** | Over SMTP after the response through `defer()`; retried by `kami:forms:deliver` from any Tick ([Forms](forms.md#retries)) | The same, retried from cron's Tick |
| **PHP settings** | The web and the command line differ: on Infomaniak, the web has 60 s and 640 MB, the command line no time limit and 1 GB | Your own `php.ini` |

## Conversions

An image's Conversion is generated by PHP on its first request, then served as a static file ([Media](media.md#conversions)); a document's or an SVG's file is copied unchanged the same way ([Media](media.md#documents-and-svg)). `kami:install` links `public/media` to the `media/` directory of `kami.media.public_disk`, which must be a local disk, and writes `public/media/.htaccess` at each run. Edits to that file are lost on the next deploy. Apache serves an existing file and adds:

| Header | Value | On |
| --- | --- | --- |
| `X-Content-Type-Options` | `nosniff` | every file |
| `Cache-Control` | `public, max-age=31536000, immutable` | every file |
| `Content-Security-Policy` | `default-src 'none'; style-src 'unsafe-inline'; img-src data:` | SVG |
| `X-Robots-Tag` | `noindex, nofollow` | every file, while the Site is not [indexable](seo.md#indexable-switch) at the install |

A missing file falls through to `index.php`, as any request does: Laravel generates or copies it and sends `nosniff`, the immutable cache and, on an SVG, the same policy too. The link needs Apache's `FollowSymLinks`, which Laravel's `public/storage` relies on already.

Which formats a Conversion is offered in depends on the host's GD and Imagick: AVIF and WebP only where one of them passes an encode test ([Media](media.md#formats)). With neither, every Conversion is JPEG or PNG, and nothing breaks. On Infomaniak, GD writes WebP but not AVIF, which only Imagick can give, when its ImageMagick build encodes it. The command line and the web may load different builds, and `kami:doctor` reports the command line's.

Two visitors asking for the same new Conversion at once wait for each other through a lock on the default cache store. The `file` and `database` stores share it between PHP workers; `array` and `null` do not, so `kami:doctor` fails on them.

Originals keep their metadata, GPS included, so they never sit where the web server reaches them. `kami:install` and `kami:doctor` fail when `kami.media.originals_disk` is a local disk whose `media/` lies under `public/`, under the public disk's `media/`, or under a target of `filesystems.links`, which `storage:link` exposes. Paths are compared once symlinks are resolved, so a site root that links to `public/` counts. A remote originals disk is not checked: keep its bucket private.

`kami:doctor` fails when `public/media` is missing or links elsewhere, and when the public disk is not local. It then writes a probe SVG under `public/media`, asks for it at the Site's URL, deletes it, and warns about each header missing from the answer. Run it where that URL can be reached: when it cannot be, the check is skipped with an information. With `APP_ENV=local`, a missing header or file is an information too: a local server, such as Herd's nginx, is not the one the site is deployed on.

## nginx

nginx reads no `.htaccess`. Serve `public/media` with the same headers, and hand a missing file to Laravel:

```nginx
location ^~ /media/ {
    add_header X-Content-Type-Options "nosniff" always;
    add_header Cache-Control "public, max-age=31536000, immutable";
    try_files $uri /index.php?$query_string;

    location ~* \.svg$ {
        add_header X-Content-Type-Options "nosniff" always;
        add_header Cache-Control "public, max-age=31536000, immutable";
        add_header Content-Security-Policy "default-src 'none'; style-src 'unsafe-inline'; img-src data:" always;
        try_files $uri /index.php?$query_string;
    }
}
```

Laravel's own nginx configuration, `try_files $uri $uri/ /index.php?$query_string;` in `location /`, already hands a missing sitemap file to Kami, which builds it ([SEO](seo.md#sitemap)). Keep it, and send no other rule's 404 for `/sitemap.xml` or `/sitemaps/`.

On a copy that is not indexable, such as staging, add `add_header X-Robots-Tag "noindex, nofollow" always;` to both blocks.

`^~` keeps a regex `location` for images, such as one setting `expires`, from taking these requests instead. In nginx, a `location` that sets a header drops every `add_header` of the levels above it, so the SVG block repeats them, and a header your `server` block sends to every response, such as `Strict-Transport-Security`, must be repeated in both. `disable_symlinks` must stay off, its default, for the link to work. Run `kami:doctor` after a change to check the headers.

## Infomaniak shared hosting

Facts measured on Infomaniak Web Hosting, on PHP 8.5, that change what a site sees:

- **The command line is not the web.** Over SSH, PHP reads its own settings: `exec` and `proc_open` are allowed there and disabled on the web. `kami:doctor` checks the PHP it runs under, which is the command line's, and prints the web's as the last visit or tick URL saw it ([Deployment](deployment.md#the-web-php)).
- **OPcache is off on the web** and cannot be turned on. Every request compiles Laravel and Filament again, so the admin is slower than on a server. Nothing in Kami depends on it.
- **`display_errors` is on on the web.** A fatal error before Laravel boots shows its message, paths included, to visitors. The starter kit turns it off: see [Deployment](deployment.md#point-the-site-at-public).
- **The database is remote.** Every query pays network latency.
- **PHP runs as the SSH user,** so `storage/` and `bootstrap/cache/` are writable once cloned. Every site of the account runs as that user too, and can read this site's files, `.env` included.
- **There is no Node** on the SSH `PATH`.
- **A missing `robots.txt` is answered by the host,** before the request reaches Laravel, with no rule for the admin. `kami:install` writes the file on every deploy ([SEO](seo.md#robotstxt)).

### The task planner

Infomaniak has no crontab: its task planner calls a URL, every 15 minutes at best. Point it at the Tick's URL:

1. Over SSH, run `php artisan kami:tick:url`, copy its `KAMI_TICK_TOKEN=` line into `.env`, then run `php artisan optimize` so the cached configuration holds it ([Deployment](deployment.md)).
2. In the Manager, under the hosting's **Cron jobs / Task planner**, add a task calling the printed URL, as often as the plan allows, with the email on failure turned on.

The URL works inside the request, within the web's 60 s, and answers `500 FAILED` when a task failed, which the planner reports. Between its calls, visits start a Tick once the last one is five minutes old ([Scheduler](scheduler.md#on-shared-hosting)).

### Mail

Infomaniak's web hosting has no `mail()` or `sendmail`: send through the SMTP server of a mail address of your Infomaniak mail service.

```dotenv
MAIL_MAILER=smtp
MAIL_SCHEME=smtps
MAIL_HOST=mail.infomaniak.com
MAIL_PORT=465
MAIL_USERNAME=site@example.com
MAIL_PASSWORD=
MAIL_FROM_ADDRESS=site@example.com
MAIL_FROM_NAME="${APP_NAME}"
```

- **The sender is the account.** Infomaniak refuses a `From` other than the address that signs in: keep `MAIL_FROM_ADDRESS` equal to `MAIL_USERNAME`. A Form puts the visitor's address on `Reply-To`, never on `From`.
- **Port 587** with `MAIL_SCHEME=smtp` (STARTTLS) also works, where 465 is blocked.
- **A daily quota per address.** Infomaniak limits how many mails an address sends a day; check the limit of your offer in the Manager. A wave of Submissions past the honeypot and the throttle can reach it: the deliveries over it fail, are retried by `kami:forms:deliver` up to five times, and `kami:doctor` reports those that failed.
- Run `php artisan optimize` after changing `.env`, then send a test Submission: `kami:doctor` reports a failed delivery with the mail server's answer.
