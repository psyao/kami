# Hosting

Kami runs on shared hosting with nothing more than PHP, a database and SSH. One code path serves shared hosting and a server: a server only adds speed.

## What the host needs

- PHP 8.5 or later, on the command line and on the web, with the extensions [Installation](installation.md#requirements) lists. The two often run different PHP builds: check both.
- One of the [supported databases](installation.md#database).
- SSH access with Composer, to run `composer install` and `php artisan kami:install` on each deploy.
- A document root on the site's `public/` directory, and HTTPS.
- Write access to `storage/` and `bootstrap/cache/` for the user PHP runs as.

## What Kami does not need

- **No cron.** Kami registers no scheduled task.
- **No queue worker.** Kami dispatches no job.
- **No Redis, Memcached or other daemon.** The starter kit uses the `file` cache store and the `database` session driver.
- **No Node on the server.** Kami's admin assets ship precompiled and `kami:install` copies them to `public/`. The site's own front assets are built before the deploy: see [Deployment](deployment.md#front-assets).
- **No `exec` or `proc_open` on the web.** Shared hosts often disable them; Kami never calls them.

## Shared hosting and a server

| Subject | Shared hosting (Infomaniak Web Hosting) | Server (Cloud Server or VPS) |
| --- | --- | --- |
| **Install and deploy** | `kami:install` over SSH, under the command line's limits (no time limit on Infomaniak) | The same |
| **Admin assets** | Precompiled in the package, copied to `public/` by `kami:install` | The same |
| **Front assets** | Built by the site in CI or on the developer's machine, then copied with the code | The same |
| **Cache and sessions** | `file` cache, `database` sessions, as the starter kit sets them | The same; Redis or Memcached possible, never required |
| **Conversions** | Generated by PHP on their first request, then served by Apache from `public/media` with the headers of its `.htaccess` | nginx serves them once given the rewrite and headers below |
| **Dates** | Kami sets the application's time zone to UTC, whatever the host's default (`Europe/Zurich` on Infomaniak) | The same |
| **PHP settings** | The web and the command line differ: on Infomaniak, the web has 60 s and 640 MB, the command line no time limit and 1 GB | Your own `php.ini` |

## Conversions

An image's Conversion is generated by PHP on its first request, then served as a static file ([Media](media.md#conversions)). `kami:install` links `public/media` to the `media/` directory of `kami.media.public_disk`, which must be a local disk, and writes `public/media/.htaccess` at each run. Edits to that file are lost on the next deploy. Apache serves an existing file and adds:

| Header | Value | On |
| --- | --- | --- |
| `X-Content-Type-Options` | `nosniff` | every file |
| `Cache-Control` | `public, max-age=31536000, immutable` | every file |
| `Content-Security-Policy` | `default-src 'none'; style-src 'unsafe-inline'; img-src data:` | SVG |

A missing file falls through to `index.php`, as any request does: Laravel generates it and sends `nosniff` and the immutable cache too. The link needs Apache's `FollowSymLinks`, which Laravel's `public/storage` relies on already.

Two visitors asking for the same new Conversion at once wait for each other through a lock on the default cache store. The `file` and `database` stores share it between PHP workers; `array` and `null` do not, so `kami:doctor` fails on them.

`kami:doctor` fails when `public/media` is missing or links elsewhere, and when the public disk is not local. It then writes a probe SVG under `public/media`, asks for it at the Site's URL, deletes it, and warns about each header missing from the answer. Run it where that URL can be reached: when it cannot be, the check is skipped with an information.

## nginx

nginx reads no `.htaccess`. Serve `public/media` with the same headers, and hand a missing file to Laravel:

```nginx
location ^~ /media/ {
    add_header X-Content-Type-Options "nosniff" always;
    add_header Cache-Control "public, max-age=31536000, immutable";
    try_files $uri /index.php?$query_string;

    location ~* \.svg$ {
        add_header X-Content-Type-Options "nosniff" always;
        add_header Cache-Control "public, max-age=31536000, immutable";
        add_header Content-Security-Policy "default-src 'none'; style-src 'unsafe-inline'; img-src data:" always;
        try_files $uri /index.php?$query_string;
    }
}
```

`^~` keeps a regex `location` for images, such as one setting `expires`, from taking these requests instead. In nginx, a `location` that sets a header drops every `add_header` of the levels above it, so the SVG block repeats them, and a header your `server` block sends to every response, such as `Strict-Transport-Security`, must be repeated in both. `disable_symlinks` must stay off, its default, for the link to work. Run `kami:doctor` after a change to check the headers.

## Infomaniak shared hosting

Facts measured on Infomaniak Web Hosting, on PHP 8.5, that change what a site sees:

- **The command line is not the web.** Over SSH, PHP reads its own settings: `exec` and `proc_open` are allowed there and disabled on the web. `kami:doctor` checks the PHP it runs under, which is the command line's.
- **OPcache is off on the web** and cannot be turned on. Every request compiles Laravel and Filament again, so the admin is slower than on a server. Nothing in Kami depends on it.
- **`display_errors` is on on the web.** A fatal error before Laravel boots shows its message, paths included, to visitors. The starter kit turns it off: see [Deployment](deployment.md#point-the-site-at-public).
- **The database is remote.** Every query pays network latency.
- **PHP runs as the SSH user,** so `storage/` and `bootstrap/cache/` are writable once cloned. Every site of the account runs as that user too, and can read this site's files, `.env` included.
- **There is no Node** on the SSH `PATH`.
