# Milestone ritual

`/to-tickets` makes the ritual the milestone's last ticket, `ready-for-human`, blocked by every other one. What it must meet is in `docs/roadmap.md` § Acceptance criteria for every milestone; these are the steps, in order.

What a later step or session needs (briefs, findings, Steve's decisions) goes in a comment on the ritual ticket, never only in a local notes file: other sessions read the repo and the tracker.

1. **Review.** `/code-review high` on `<last tag>...HEAD` for `src`, `database`, `resources` and `config`, with `docs/agents/coding-standards.md`. Reproduce what can be, on the engines concerned. Defects to fix before the release go in one ticket; the others go to `needs-triage` with a target.
2. **Version.** Read `docs/development.md` § Releases, and name the number the milestone's changes call for. If it differs from the release pull request's, a `Release-As:` footer sets it, with its `UPGRADING.md` section when it is a minor. Read that section against `git log <last tag>..HEAD`: each change a site must act on has its line, `!` or not (`ticket-session.md` step 3).
3. **Debt.** `/ponytail:ponytail-debt`, then `/ponytail:ponytail-audit`, on `main`. Each audit finding kept goes where step 1's do: the fixes ticket if it should hold the release, else `needs-triage` with a target.
4. **Playground.** Steve tries the features from the guides alone, after `dev-main` and `kami:install`, with `kami:doctor --strict` clean. An agent runs these trials only when he asks, and the ticket then says so with what it left untried. Before an agent's trials, Steve runs `herd secure` on the playground's site, which an agent does not do on his machine, so that a Form is also posted from a real browser (#536). Each problem is a `friction` issue, kept in the milestone only if it should hold the release.
5. **Triage.** Each `needs-triage` issue opened during the milestone has a target in a comment.
6. **Release.** Steve clicks **Approve and run** on the release pull request. After a `docs:`, `ci:` or `test:` commit, `gh pr update-branch` brings its CI up to date with `main`. Merge once the seven jobs are green.
7. **After Packagist.** The starter kit's `next` merges into its `main` with the new `^0.x` constraint in place of `dev-main`, and `laravel new --using=psyao/kami-starter` is checked to install it. `next` is then reset to `main` (a force-push) and `psyao/kami: dev-main` committed on it again (ADR 0039). The playground leaves `dev-main` for the new version.
8. **Retro.** Steve runs `/mattpocock-skills:retro` over the milestone's ticket sessions, starting with those that went worst (rework, a refused push, step 1's findings), then over the ritual itself (the playground, the release, the starter kit). It comes after the release so that the release never waits on it and the ritual's own friction is in it. Each candidate kept lands as a `docs:` or `ci:` pull request, or goes to `needs-triage` with a target.
9. **Close.** Close the ritual, the spec and the Milestone last, each once what it tracks is done.
